## Problem

Home currently shows a horizontal scrollbar even when the visible content appears to fit within the viewport. This is a baseline UI integrity bug on the default entry surface: it makes the product feel visually unstable, suggests layout breakage, and weakens first-use trust.

The issue scope is intentionally narrow:

- Surface: Home / entry view only.
- Symptom: false horizontal overflow on viewport-fitting layouts.
- Expected behavior: when Home content fits the available width, the page remains horizontally locked and does not expose a horizontal scrollbar.

- Issue: `lefarcen/open-design#360`

## Goals

- Remove the unnecessary horizontal scrollbar from the Home page when content fits the viewport.
- Fix the underlying overflow source instead of masking it with a broad global `overflow-x: hidden` patch.
- Keep the fix local to the Home entry surface and its immediate layout containers.
- Add a regression check that fails when Home reintroduces viewport-width overflow.

## Success Criteria

- Home does not show a horizontal scrollbar when visible content fits the available viewport width.
- The fix removes the root overflowing element or layout rule instead of suppressing overflow globally.
- The change stays limited to the Home entry surface and immediately related containers.
- Automated coverage protects the no-false-horizontal-overflow invariant.

## Non-Goals

- Redesigning the Home page.
- Refactoring unrelated workspace, project-view, or chat-layout overflow behavior.
- Changing rail, plugin gallery, or modal behavior outside what is required to eliminate the Home overflow regression.
- Introducing new product capabilities, routes, contracts, or CLI surface.

## Current Implementation Context

The Home surface is implemented as a web-only entry layout and is already reasonably isolated:

- `apps/web/src/components/EntryView.tsx` delegates Home rendering into the entry shell.
- `apps/web/src/styles/home/index.css` owns the Home stylesheet bundle.
- `apps/web/src/styles/home/entry-layout.css` owns the shell and scroll container layout.
- `apps/web/src/styles/home/home-hero.css` owns the centered Home hero and chip/tab rows.

This makes the likely bug class a local CSS regression such as:

- a child width computed from viewport units instead of the available container width;
- a flex/grid child missing `min-width: 0`;
- horizontal padding, transforms, or absolute-positioned affordances escaping the intended width budget;
- a collapsed rail or tooltip/popover element still contributing to scroll width.

## Approach

### 1. Reproduce and isolate the overflow source

Start by reproducing the issue on Home at common desktop widths and at least one narrower viewport. Inspect the actual scroll width delta and identify which Home container exceeds `document.documentElement.clientWidth`.

Investigation should prioritize:

- entry shell and main scroll container rules in `entry-layout.css`;
- Home hero width, padding, and chip rows in `home-hero.css`;
- plugin/recent-project sections only if they are present in the overflow path;
- collapsed-rail and tooltip states, since visually hidden elements can still affect layout width.

### 2. Fix the root cause at the narrowest container

Apply the smallest structural CSS fix that restores the invariant:

> No Home-owned layout container should widen the page beyond the viewport when its visible content fits.

Preferred fixes:

- replace viewport-based widths with container-relative sizing where appropriate;
- add `min-width: 0` to flex/grid children that should shrink;
- constrain full-width rows with `width: 100%` plus safe `max-width`;
- ensure off-canvas or collapsed rail content is clipped by the correct container, not merely visually hidden.

Avoid:

- adding page-global `overflow-x: hidden`;
- clipping the root entry container in a way that would hide legitimate overflow bugs or break positioned UI;
- moving the bug into another Home subsection.

Current technical recommendation, pending the required human decision:

- Prefer `A resize handle` if the overflow source is a specific handle, rail edge, or width budget escaping its container.
- Treat `B overflow-x` only as a last-resort mitigation and not the default fix, because it can mask the underlying regression instead of removing it.

### 3. Add a regression spec before or alongside the fix

Follow the repository bug workflow and encode the issue as a red spec first when practical.

Most likely validation shape:

- add a focused web test that renders the Home entry view and asserts no horizontal overflow at representative viewport widths, or
- add a Playwright/e2e check if the bug depends on real layout measurement that a lower layer cannot reliably observe.

The assertion should target the user-visible invariant, for example that Home does not produce `scrollWidth > clientWidth` in the steady state.

## Implementation Scope

- In scope: Home entry layout containers, Home-specific CSS, and the narrowest supporting component markup needed to remove the false overflow.
- In scope: a focused automated regression test at the cheapest layer that can reliably observe the bug.
- Out of scope: unrelated workspace or project-view layout cleanup, global overflow policy changes, or broader Home redesign work.

## Risks

- A broad overflow clamp could hide a real layout regression without fixing it.
- Home contains multiple horizontally arranged UI regions; fixing one row may expose another latent offender.
- Rail collapse/expand behavior may interact with scroll width if hidden content still participates in layout.
- Tooltip or popover affordances may require explicit containment so that interactive overlays do not become layout width contributors.

## Validation

Minimum validation for the implementation PR:

1. Add or update a red-to-green automated regression test covering Home horizontal overflow.
2. Run `pnpm --filter @open-design/web typecheck`.
3. Run the package-scoped test command that covers the new regression spec.
4. Perform manual browser verification on Home at:
   - one standard desktop width;
   - one narrower width where wrapping/chip density changes;
   - rail collapsed and rail expanded states, if relevant to the root cause.

Human verification should confirm:

- no horizontal scrollbar appears when Home content fits;
- no Home content is visually clipped by the fix;
- centered hero, chip rows, and nearby sections still align correctly.

## Acceptance Criteria

- Home no longer shows a horizontal scrollbar on viewport-fitting layouts.
- The fix is localized to the Home entry surface or its immediate containers.
- The implementation addresses the actual overflowing element instead of relying on a global overflow suppression patch.
- A regression test protects against reintroducing the false horizontal scrollbar.
